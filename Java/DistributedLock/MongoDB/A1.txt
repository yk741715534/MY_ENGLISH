使用 MongoDB 的 upsert 更新某个字段（唯一索引），根据返回值，来判断是否更新成功。利用这种机制来做分布式锁，合理吗？

使用 MongoDB upsert 的返回值来判断是否获得分布式锁，不推荐，存在严重问题。下面分析原因并提供更好的方案。

🚫 为什么不合理？
1. 并发竞争问题
javascript
下载
复制
// 常见错误实现
db.locks.updateOne(
  { _id: "order_lock", owner: null },  // 查询条件
  { $set: { owner: "server_A" } },     // 更新
  { upsert: true }                      // 不存在则创建
);

问题：两个进程可能同时发现文档不存在，都执行 upsert 创建成功，导致锁被重复获取。

2. 返回值模糊

matchedCount: 匹配到的文档数

upsertedCount: 新插入的文档数（通常为 0 或 1）

modifiedCount: 修改的文档数

但这些返回值无法可靠判断哪个客户端获得了锁。即使 upsertedCount=1，也可能多个客户端都看到这个结果。

3. 缺乏原子性保证

虽然单文档操作是原子的，但“检查-插入/更新”逻辑在并发时不可靠。真正的锁需要严格的“测试并设置”原子性。

✅ 正确的 MongoDB 分布式锁方案
方案1：使用 findOneAndUpdate（推荐）
javascript
下载
复制
const lock = await db.locks.findOneAndUpdate(
  {
    _id: "order_lock",
    $or: [
      { owner: null },
      { expireAt: { $lt: new Date() } }  // 支持锁超时
    ]
  },
  {
    $set: {
      owner: "server_A",
      expireAt: new Date(Date.now() + 30000)  // 30秒后过期
    },
    $setOnInsert: { createdAt: new Date() }
  },
  {
    upsert: true,
    returnDocument: 'after'  // 返回更新后的文档
  }
);

if (lock.owner === "server_A") {
  // 成功获取锁
} else {
  // 被其他客户端抢走
}

🔐 生产级实现要点

复制
class MongoDistributedLock {
  constructor(collection, resource, owner, ttl = 30000) {
    this.collection = collection;
    this.resource = resource;
    this.owner = owner;
    this.ttl = ttl;
    this.lockId = null;
  }

  async acquire() {
    const now = new Date();
    const expireAt = new Date(now.getTime() + this.ttl);

    try {
      const result = await this.collection.findOneAndUpdate(
        {
          _id: this.resource,
          $or: [
            { owner: null },
            { expireAt: { $lt: now } },
            { owner: this.owner }  // 支持重入
          ]
        },
        {
          $set: { owner: this.owner, expireAt },
          $setOnInsert: { createdAt: now }
        },
        { upsert: true, returnDocument: 'after' }
      );

      if (result.owner === this.owner) {
        this.lockId = result._id;
        return true;
      }
      return false;
    } catch (err) {
      // 处理唯一键冲突等异常
      return false;
    }
  }

  async release() {
    if (!this.lockId) return;

    await this.collection.updateOne(
      { _id: this.resource, owner: this.owner },
      { $set: { owner: null } }
    );
  }
}
⚠️ 使用分布式锁的注意事项

设置合理的 TTL：避免死锁，也要避免过早过期

实现锁续期：长任务需要定期刷新过期时间

考虑时钟同步：多服务器时钟差异可能影响 TTL

添加重试机制：获取失败时应有退避重试

记录锁日志：便于排查死锁问题

📈 推荐方案

对于大多数场景，推荐：

使用 findOneAndUpdate​ 的原子操作

配合 唯一索引​ 防止重复

实现 锁续期​ 机制

考虑使用 Redisson​ 或 Curator​ 等成熟框架

总结：直接依赖 upsert 返回值做分布式锁是危险的。应使用原子的“测试并设置”操作，或直接采用成熟的分布式锁实现。

为什么 返回值 upsertedCount=1，不能用于判断是否获取锁成功

核心原因：upsertedCount=1只表示文档被创建了，但在高并发下，这不保证是你创建的，也不能保证你是唯一创建者。让我用一个实际场景来演示这个陷阱：

🔄 并发竞争的场景重现

假设两个进程 几乎同时​ 执行相同的 upsert 操作：

javascript
下载
复制
// 进程A
const resultA = await db.locks.updateOne(
  { _id: "order_lock" },  // 查询条件
  { $set: { owner: "server_A" } },
  { upsert: true }
);
// 返回: { upsertedCount: 1, matchedCount: 0, ... }

// 进程B（几乎同时执行）
const resultB = await db.locks.updateOne(
  { _id: "order_lock" },  // 查询条件
  { $set: { owner: "server_B" } },
  { upsert: true }
);
// 返回: { upsertedCount: 1, matchedCount: 0, ... }

问题来了：两个进程都看到了 upsertedCount: 1，都认为自己成功创建了文档，获得了锁。但实际上，只有一个真的创建成功了。

🧠 背后的机制解释
1. 竞态条件（Race Condition）
复制
时间线：
t1: 进程A检查 → 文档不存在
t2: 进程B检查 → 文档不存在（A还未完成插入）
t3: 进程A插入文档成功 → upsertedCount=1
t4: 进程B尝试插入，但实际执行了更新（因为A已创建）
    然而MongoDB可能返回 upsertedCount=1，因为它以为自己在创建
2. MongoDB upsert 的实际行为
javascript
下载
复制
// MongoDB 的 upsert 逻辑简化版
function updateWithUpsert(filter, update, options) {
  const existingDoc = collection.findOne(filter);

  if (existingDoc) {
    // 更新现有文档
    updateDocument(existingDoc, update);
    return { matchedCount: 1, modifiedCount: 1, upsertedCount: 0 };
  } else {
    // 创建新文档
    const newDoc = { _id: generateId(), ...update };
    insertDocument(newDoc);
    return { matchedCount: 0, modifiedCount: 0, upsertedCount: 1 };
  }
}

关键点：在并发下，两个进程可能都进入 else 分支，认为自己创建了文档。

3. 网络延迟和时序错觉
复制
客户端视角 vs 服务器实际发生的情况：

客户端A: 发送请求 → 收到响应(upsertedCount=1) → 认为"我创建的！"
客户端B: 发送请求 → 收到响应(upsertedCount=1) → 认为"我创建的！"

服务器实际:
1. 收到A请求 → 创建文档
2. 收到B请求时文档已存在 → 本应返回 matchedCount=1
   但由于时序问题，可能B认为自己创建了

📊 为什么会有这种误解？

人们常错误地认为：

复制
upsertedCount=1 → 我插入了文档 → 我获得了锁

但实际上应该是：

复制
upsertedCount=1 → 本次操作是插入操作 → 但可能并发时多个都返回1

🎯 核心原则

记住分布式锁的黄金法则：

仅仅通过操作返回值判断是否获得锁是不够的，必须能确定性地知道当前锁的持有者是谁。

你的判断依据必须满足：

原子性：检查和设置必须是同一个原子操作

排他性：只能有一个成功者

可验证性：成功者必须能验证自己是持有者

防误判：失败者必须知道自己失败
