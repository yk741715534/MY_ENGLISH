# 系统设计入门

## 设计框架

### 四步法

1. **需求明确**
   - 功能需求：系统能做什么？
   - 非功能需求：性能、可用性、扩展性

2. **容量估算**
   - DAU（日活用户）
   - QPS（每秒查询数）
   - 存储容量

3. **系统设计**
   - API 设计
   - 数据模型
   - 组件选型

4. **扩展优化**
   - 缓存策略
   - 分片方案
   - 容灾设计

## 案例一：短链接系统

### 需求
- 输入长 URL，生成短 URL
- 访问短 URL，重定向到长 URL
- 支持自定义短链接
- 统计点击次数

### 估算
- 假设：1 亿 URL/月
- QPS：1000M / (30 * 86400) ≈ 400/s，峰值 2000/s
- 存储：每条 500B，5 年 ≈ 30TB

### 设计

**API**：
```
POST /shorten → 返回短链接
GET /{shortCode} → 301 重定向
```

**短码生成方案**：
1. 哈希截断（MD5/Base62）→ 可能冲突
2. 自增 ID + Base62 编码 → 简单可靠
3. 预生成短码池 → 分布式友好

**存储**：
- MySQL：短码 → 原始 URL 映射
- 分片：按短码哈希分片

**优化**：
- 缓存热点短链接
- 301 永久重定向（浏览器可缓存）

## 案例二：新闻 Feed

### 需求
- 发布动态（关注者能看到）
- 查看 Feed 流
- 点赞、评论

### 两种 Feed 模型

**推模式（写扩散）**：
- 发布时写入所有关注者的 inbox
- 优点：读快
- 缺点：写慢，大 V 写放大严重

**拉模式（读扩散）**：
- 读时合并关注列表的最新动态
- 优点：写快
- 缺点：读慢，关注多时性能差

**混合模式**：
- 普通用户：推模式
- 大 V：拉模式

### 存储
- 动态表：id, user_id, content, created_at
- 关注表：follower_id, followee_id
- Feed 表（推模式）：user_id, post_id, created_at

## 案例三：聊天系统

### 需求
- 一对一聊天
- 在线状态
- 消息已读
- 历史记录

### 技术选型

**连接层**：WebSocket 长连接

**消息存储**：
- 消息表：id, from_id, to_id, content, created_at, status
- 会话表：user1_id, user2_id, last_message

**在线状态**：Redis Set 存在线用户

**消息投递**：
- 在线：直接通过 WebSocket 推送
- 离线：存入数据库，上线后拉取

### 扩展

**消息队列**：Kafka 削峰填谷

**分片**：按会话 ID 分片

## 案例四：限流器

### 需求
- 限制 API 调用频率（如每秒 100 次）
- 返回 429 状态码
- 支持不同用户不同限制

### 算法

**固定窗口**：
- 每秒一个窗口，计数
- 问题：边界突刺（59 秒和 01 秒可能瞬时 2 倍）

**滑动窗口**：
- 精确控制，但内存开销大

**令牌桶**：
- 以固定速率放入令牌
- 请求消耗令牌
- 支持突发流量（桶内有令牌）

**漏桶**：
- 请求先进队列
- 以固定速率处理
- 强制平滑流量

### 实现

**Redis + Lua 脚本**：原子操作保证正确性

```lua
-- 简单令牌桶
local tokens = redis.call('GET', KEYS[1])
if tokens and tonumber(tokens) > 0 then
    redis.call('DECR', KEYS[1])
    return 1
else
    return 0
end
```

## 常见概念

### CAP 定理

分布式系统最多同时满足三项中的两项：
- **C**onsistency 一致性
- **A**vailability 可用性
- **P**artition tolerance 分区容错

### BASE 理论

- **Basically Available** 基本可用
- **Soft state** 软状态
- **Eventually consistent** 最终一致性

### 一致性哈希

解决普通哈希在节点增减时大量数据迁移的问题

**虚拟节点**：解决数据分布不均匀

### 分布式 ID 生成

1. **UUID**：无序，索引性能差
2. **数据库自增**：单点瓶颈
3. **Snowflake**：时间戳 + 机器 ID + 序列号，趋势递增

```
| 1 bit | 41 bits 时间戳 | 10 bits 机器ID | 12 bits 序列号 |
```
